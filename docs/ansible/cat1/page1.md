# 構成管理の基礎

## 1. 構成管理とは

**構成管理（Configuration Management）** とは、サーバやネットワーク機器などのインフラの「あるべき状態」を定義・記録し、その状態を維持・管理する手法です。

手動でサーバを設定していた場合、以下のような問題が発生しがちです。

| 問題 | 内容 |
|------|------|
| **属人化** | 担当者しか手順を知らず、異動・退職時に引き継ぎが困難になる |
| **設定ミス** | 手順書を見ながらの手作業は、入力ミスや手順漏れが起こりやすい |
| **環境差異** | 開発・ステージング・本番で微妙に設定が異なり、「本番だけ動かない」問題が発生する |
| **再現性の欠如** | サーバが壊れたとき、同じ状態を一から再構築するのに多大な時間がかかる |

構成管理ツールを使うことで、これらの問題を解決し、インフラを **コードとして管理（Infrastructure as Code）** できます。

## 2. 自動化が求められる背景

クラウドやコンテナ技術の普及により、管理対象のサーバ台数は爆発的に増加しました。

```
[従来]
  サーバ数: 数台〜数十台
  → 手動でも何とかなった

[現在]
  サーバ数: 数百台〜数千台（クラウド・コンテナ）
  → 手動管理は現実的ではない
```

また、以下のようなビジネス要求も自動化を後押ししています。

| 要求 | 内容 |
|------|------|
| **リリース頻度の向上** | 週1回→1日複数回のデプロイが当たり前になった |
| **コスト削減** | 手作業の工数を減らし、エンジニアをより付加価値の高い業務へ |
| **障害対応の迅速化** | サーバ障害時に素早く同じ環境を再構築できることが求められる |

## 3. Ansibleとは

**Ansible** はRedHat社が開発したオープンソースの構成管理ツールです。  
以下の特徴から、構成管理ツールの中でも特に広く普及しています。

| 特徴 | 説明 |
|------|------|
| **エージェントレス** | 管理対象ノードにAnsible専用のソフトウェアをインストール不要。SSHで接続して操作する |
| **YAMLで記述** | 設定ファイル（Playbook）をYAML形式で書くため、読み書きしやすい |
| **冪等性（べきとうせい）** | 何度実行しても結果が同じになるように設計されている |
| **豊富なモジュール** | パッケージ管理・サービス制御・ファイル操作など、多数のモジュールが標準搭載されている |

### Ansibleの全体像

```
┌─────────────────────────────────────────────┐
│               管理ノード                     │
│  ┌─────────────────────────────────────┐    │
│  │  Ansible                            │    │
│  │  ・Playbook（自動化の手順書）         │    │
│  │  ・Inventory（管理対象リスト）        │    │
│  └──────────────┬──────────────────────┘    │
└─────────────────┼───────────────────────────┘
                  │ SSH
       ┌──────────┼──────────┐
       ▼          ▼          ▼
  ┌─────────┐ ┌─────────┐ ┌─────────┐
  │ server1 │ │ server2 │ │ server3 │
  │（被管理）│ │（被管理）│ │（被管理）│
  └─────────┘ └─────────┘ └─────────┘
```

- **管理ノード（Control Node）**: Ansibleをインストールし、Playbookを実行するサーバ
- **被管理ノード（Managed Node）**: Ansibleに操作されるサーバ（エージェント不要）

## 4. 主な競合ツールとの比較

| ツール | 特徴 | 向いているケース |
|--------|------|------------------|
| **Ansible** | エージェントレス・YAML記述・シンプル | 汎用的な構成管理・小〜中規模 |
| **Chef** | Rubyで記述・エージェント必要 | 大規模環境・細かい制御が必要な場合 |
| **Puppet** | 宣言型・エージェント必要 | 大規模環境・厳密な状態管理 |
| **Terraform** | インフラのプロビジョニングに特化 | クラウドリソースの作成・管理 |

:::tip
AnsibleとTerraformは役割が異なります。  
Terraformでサーバを「作り」、Ansibleでサーバを「設定する」という組み合わせが現場でよく使われます。
:::
